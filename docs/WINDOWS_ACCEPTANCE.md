# Windows 实机验收

此步骤必须在实际登录微信的 Windows 上进行。WSL 内的模拟测试无法替代 Windows 权限、进程布局和真实消息 schema 验证。当前不声称已经通过以下实机验收。

1. 按 README 创建 Windows `.venv` 并安装项目。运行 `doctor --json`，检查 Python 位数报错、微信完整版本、所选 `db_storage`。
2. 自己登录账号，运行 `prepare --data-dir "...\db_storage" --json`。确认 `verified_databases` 覆盖联系人库和所有 `message_N.db`；只拿到部分密钥必须失败。
3. 如果 `ACCESS_DENIED`，根据错误检查终端用户和微信运行权限；如果 `KEY_NOT_FOUND`，打开目标私聊和历史记录后重跑一次。仍失败则停止，依据完整版本在本机适配 keyscan，不反复启动、关闭或修改微信。
4. 记下目标私聊中若干早期、中间和最新普通文字的时间与发送方向，包括一条长文字、一条带换行/表情的文字，以及两条重复发送的相同文字。
5. 从托盘正常退出微信，运行 `contacts --query "目标昵称" --json`。确认目标稳定 ID；存在重名时用不同 ID 测试，导出不能自动选第一位。
6. 运行 `export --target "稳定ID" --out "单独的目录" --json`，检查 TXT/JSONL 与第 4 步记录一致；核对 `manifest.json` 中全部分片、文本数量与跳过类型。随后可重新打开微信核对更多历史。
7. 再正常退出微信，在数据未变化情况下重复导出，应复用相同结果；手工修改已导出 TXT 后重跑应报 `OUTPUT_EXISTS`，不能覆盖修改。
8. 微信运行中尝试 export 应报 `NEED_EXIT`。不要为了测试在真实数据目录制造 WAL 或篡改数据库；这些破坏场景已经使用合成样本测试。

## WAL 验收边界

- 正常退出后若自然残留 WAL，记录数据库及 WAL 的大小、mtime 和 SHA-256，导出后确认源文件未变；不要删除、手工 checkpoint 或修改真实日志。
- 核对 `manifest.json` 来源清单中对应数据库的嵌套 `wal` 文件名、大小和 SHA-256，并对照微信确认最新已提交文字未遗漏。无 WAL 的样本不能作为 WAL 实机验证通过的依据。
- 工具只在私有加密副本上重放已提交事务，再解密查询。同代未提交帧须校验但不重放；完整帧头盐不匹配后的旧代或预分配尾部忽略，允许非整帧尾部。活动代残缺头部/帧、同代校验和或页认证损坏必须失败，不得静默退回仅主库导出；这些异常只在合成样本或独立测试副本上验证。
- 非空 `-journal` 仍返回 `NEED_CLEAN_EXIT`；无效 WAL 返回 `INVALID_WAL`，页认证失败返回 `PAGE_AUTH_FAILED`。保留原文件，在本机核查，不以删除日志绕过错误。
- 本流程仍要求微信退出，不验收在线读取，也不将某个版本的成功推广为全部微信/WCDB 版本兼容。

需要协作排错时，提供 JSON 中的错误码、微信完整版本、缺失列名及代码位置即可。密钥、内存转储和聊天数据库都留在本机。架构故意提供可替换的内存 reader 和 schema adapter，Windows 侧可以只调整对应模块。

完成后在本地记录：微信版本、Python 位数、prepare 覆盖数、目标 ID、导出条数、人工核对结果。未经这一步，不将“单元测试通过”标记为“支持你的最新微信”。
